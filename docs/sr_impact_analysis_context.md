# SR 영향분석 플러그인 — 프로젝트 컨텍스트 요약

## 0. 이 문서의 목적
새 세션에서 이 문서만 읽으면 프로젝트의 정체성/목표/방향/미결사항이
복원되도록 하는 컨텍스트 스냅샷. (최종 갱신 기준: 아래 결론들 반영)

## 1. 도구의 진짜 정체 (가장 중요)
- 이 도구는 "코드 완전성을 강제하는 게이트(ENFORCE)"가 아니다.
- 이 도구는 **운영담당자가 '변경 영향 분석서'를 빠르고 누락 없이
  작성하도록 돕는 조력자**다.
- 사용자 = 운영담당자 (현업도 개발담당자도 아님).
- 최종 산출물 = 변경 영향 분석서의 **6번 "변경대상 CI 목록"** 초안.

## 2. 업무 프로세스 (도메인 맥락)
- 현업이 요건서 작성 → 운영담당자에게 설명.
- 운영담당자가 요건 분석 → **변경 영향 분석서** 작성 (도구가 돕는 지점).
- 분석서가 나와야 개발 단계 진입 가능.
- 개발담당자는 분석서에 적힌 파일만 수정 가능.
- 분석서 벗어나는 수정/인터페이스 추가 필요 시 → 운영담당자에게 요청
  → 분석서 변경 → **현업 변경관리자 결재 필요**.
- ⇒ 핵심 함의: 분석서의 **누락 = 재결재 = 조직 전체 비용**.

## 3. 변경 영향 분석서 양식 구조
- 1번 개발요청사항: 요건 분석 + 파일단위 변경명세(1-1,1-2,1-3...).
  (도구가 초안 던지되 세부 로직은 사람 확정)
- 2번 개발요청 추가/삭제
- 3번 타 시스템 업무/인터페이스 (⚠ 정적분석이 놓치기 쉬움, recall 취약)
- 4번 IT SMART 적용 여부
- 5번 기타 검토 항목
- **6번 변경대상 CI 목록** (도구의 핵심 출력):
  칸 = 유형(온라인/배치) | 구분(신규/변경) | 프로그램ID(경로) |
       프로그램명 | 개발요건 매핑(1번 항목번호) | 비고
- 실제 APC 사례: SR 하나 = SVO/SVC/SVCImpl/BIZ/DEM 5개 CI 세트.
  ⇒ 우리가 만든 AnyframeApRuleset companion 룰이 현실과 정확히 일치함(검증됨).

## 4. 목표 지표 (기존 목표 폐기 후 재정의)
- ❌ 폐기: ENFORCE 전환, 500-case, FP≤5%, blocking 게이트.
  (이유: 최종책임은 사람, 누락은 드묾, blocking은 순비용)
- ✅ 신규 목표: **간단 SR에 대해 6번 CI 목록 초안의 recall ≥ 90%**.
- recall > precision (비대칭). 애매하면 빼기보다 넣는 쪽.
  (누락 1개 > 과잉 5개 만큼 비쌈, 누락=재결재이므로)

## 5. 아키텍처 (/analyze 7단계) 및 냉정한 평가
1. 라우팅(WebviewActionRouter) — Skip Mode(!) 시 신뢰도 낮춰야
2. Stage 0 Clarify — ⚠ 무질문 통과 시에도 "내 해석 한줄" 노출 필요
3. Stage 0.5 Scope — ⚠ 범위 축소=recall 리스크. "제외된 것"을 확인시켜야
4. Stage 1 파일탐색 (Seed→홉확장→점수압축→신규탐지)
   - ⚠⚠ 최대 취약점: Phase 3 "상위 30개 압축"에서 진짜 파일이
     조용히 탈락 = 보이지 않는 recall 실패. 로그에 안 남음.
   - Stage 1은 "넓게", Stage 4는 "좁게" — 튜닝 방향이 정반대.
     (anchor scope 버그 교훈을 Stage 1에 잘못 적용 금지)
5. Stage 2 경로보정 — 환각경로 vs 신규생성 구분 명확히
6. Stage 3 LLM 재검증 + 의존성 정렬
7. Stage 4 완결성가드(SHADOW) — companion 힌트 제공(막지 않음)
8. 결과반환 — ⇒ 6번 CI 목록 양식에 맞춰 재설계 필요

## 6. 확정된 설계 방향
- 앞 2단계(Stage 0, 0.5)는 "입력 정렬": 조용한 결정을 노출/확인시키게 보정.
  - Stage 0: 무질문 시 자기해석 한줄 노출.
  - Stage 0.5: 포함이 아니라 "제외 목록"을 확인.
- 이후는 **여러 라운드 왕복 소통**으로 결과물 완성:
  - 첫 판은 넓게(좁으면 왕복이 우물 안에서만 돔).
  - 파일을 3분류(확실/아마/애매)로 제시, 사람에겐 "애매+누락"만 질문.
  - 사람이 추가한 파일 = 새 seed → 재확장(단순반복 아닌 수렴).
  - 종료조건: 변화 없으면 확정 / 계속 확장되면 "복잡SR, 수동권장"으로 물러남.
  - 왕복 로그 = 감사추적 + 결재 방어논리.
- 자기 신뢰도 분류: 점수분포가 뚜렷하면 간단SR(짧게 확인),
  컷라인 근처 촘촘하면 복잡SR(적극 개입).
- 원칙: "90%인 척"보다 "자신 없을 때 물러서는 정직함"이 채택의 열쇠.
- Stage 1 내부 개입 설계 (Phase별, 조기개입=첫째안 채택):
  * Phase 1 Seed 확정 직후: 개입가치 최고(오류가 뒤로 증폭되므로 조기교정).
    단 seed 명확+범위 좁으면 자동통과. 물을 땐 "내 해석 한줄" 근거 함께.
  * Phase 2 홉확장: 사람 개입 X(넓게 가야 함). 대신 홉수/후보수 계측만.
  * Phase 3 점수압축: 30개 컷 대신 3구간분류(고신뢰/중/경계). 경계만 질문.
    점수분포로 자기신뢰도 판단 → 뚜렷하면 가볍게, 촘촘하면 적극개입.
  * Phase 4 신규탐지: 신규/인터페이스는 신뢰도 본질적으로 낮음 명시.
    인터페이스는 확신 없어도 일단 플래그(재결재 단골이므로).
- 개입의 3조건: ①신뢰도게이트로 멈춤여부 판단 ②멈추면 최대한 일찍
  ③멈출 땐 근거+신뢰도 함께 제시.

## 7. 검증 자산 / 제약
- APC=Anyframe(AnyframeApRuleset), ISM=SpringMVC+MyBatis(SpringMvcMybatisRuleset).
- member-market=Spring Boot JPA(SpringBootJpaRuleset, companion 약함).
- ⚠ APC/ISM 소스 없음 → 로컬 실행 불가. 플러그인 zip 내부망 반입만 가능.
- member-market은 로컬 runIde로 반복 테스트 가능(유일한 빠른 검증환경).
- ★ ground-truth 금맥: **과거 완료 SR들의 변경영향분석서(6번 CI 목록)**
  가 곧 정답 데이터. 소스 없어도 "6번 목록 재현율" 실측 가능.

## 10. 책임 구조 (설계의 하드 제약)
- 결과에 대한 책임은 사람(운영담당자)이 진다. 도구는 대신 결정하지 않는다.
- ⇒ 자동화(자동 포함 승격 등)도 사람의 명시적 승인 필수.
- ⇒ 최종 승인 목록의 모든 항목은 투명하게 노출(침묵 금지).
     사람은 아는 것에만 책임질 수 있으므로.
- 명시적 승인 = 근거+신뢰도가 모두 보이는 상태의 서명. 이 기록=감사추적.
- ⚠ 단, "다 애매합니다"로 책임 회피 금지. 도구는 신뢰도를 정직히 차등
     표시해 사람의 검토 부담을 배분해야 함(자신있는 건 자신있다고 말할 것).

## 11. 개입 강도 진화 (느슨→조임, 데이터 기반)
- 초기: 임계값 낮게(자주 개입). 목적=신뢰 적립(사람이 도구 판단품질 관찰).
  단 개입 시 항상 근거+신뢰도(점수) 제시 → 시끄러움이 아닌 정직함.
- 조이기: 감이 아니라 데이터로. 왕복로그에 "제안→사람이 실제 채택했는가"
  축적(= SHADOW satisfied 플래그의 확장 = companion 룰별 실제 채택률).
  채택률 안정적으로 높은 룰만 "질문→자동포함"으로 승격.
- ⇒ 폐기했던 RECOMMENDED→MANDATORY 승격 아이디어가 여기서 부활:
  단 blocking이 아니라 "개입 강도 조절"이라는 어시스턴트다운 형태로.
- 조이기 결정도 사람의 명시적 승인 필수(책임구조, 10번).
- 조인 항목도 결과엔 항상 표시(안 물어봄 ≠ 안 보여줌). 사람이 되돌릴 여지.
