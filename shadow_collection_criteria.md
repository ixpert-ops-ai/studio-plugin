# SHADOW Collection & Enforcing Transition Criteria

This document defines the quantitative criteria and processes required before transitioning the `CompletenessGuard` from `SHADOW` mode to `ENFORCING` mode. Because we are collecting data via **Natural Occurrence (B)**, we must ensure the sample size is statistically significant and representative of the organization's workloads.

> [!IMPORTANT]
> Do not enable `ENFORCING` mode until all prerequisites on this checklist are met. Premature enforcement based on an insufficient denominator can lead to blocking valid developer workflows.

## 1. Collection Volume & Diversity
The denominator for our False Positive (FP) rate calculation is **`unknownBlockEvents`** (SRs containing at least one unknown violation). Known debt (e.g., `ISM_16_XML`) is excluded from this denominator. However, to understand the true context of these blocks, we must track the total evaluated SRs.

- [ ] **Total Evaluated SRs**: Record the total number of SRs evaluated during the collection period (from `totalEvaluatedEvents`). This provides the baseline context (e.g., "50 unknown blocks out of 2,000 total SRs").
- [ ] **Minimum Unknown Block Events**: Collect at least **50** `unknownBlockEvents` across the organization.
- [ ] **Framework Diversity**:
  - [ ] At least **20** unknown block events must originate from the `apc` domain.
  - [ ] At least **20** unknown block events must originate from the `ism` domain (Spring MVC + MyBatis).
- [ ] **Data Loss Check**: The `totalSkippedLines` (Parser broken lines) must be less than **5%** of the total evaluated logs. If data loss is higher, investigate file writing/IDE crashes before proceeding.

### 1.2 The "Verified Profile" Protocol
The following mandatory steps must be executed and confirmed before declaring a project's framework/architecture profile "Verified":
1. **Target Identification**: Extract a representative sample of files (e.g., `<Target>.java`, `<Target>Impl.java`, `mapper.xml`) from the target project.
2. **Graph Structure Verification**: Execute `Get-Content <graph.json> | Select-String <Target>` to confirm the target file exists in the metadata graph.
3. **Link Verification**: Ensure a `linkType` (e.g., `namespace_binding`, `injection`) correctly connects the components (e.g., DAO to XML).
4. **[CRITICAL] Both Ends Verification**: It is NOT enough to just see a `namespace_binding` edge on the XML. You MUST open the graph JSON and explicitly verify that the Java node on the other end has the correct `fileType` and `layer` (e.g., `REPOSITORY`, `PERSISTENCE`). If it is misclassified (e.g., as `INTERFACE` and `COMMON`), the guard will fail, resulting in False Positives.
5. **Dry Run (SHADOW)**: The guard must be evaluated against this profile without crashing, and any False Positives (like role over-enforcement) must be documented.

## 2. File-Level Over-Enforcement (The known unknown)
Certain framework profiles enforce "All companions must exist at the file level." For example, a `CompanionTrigger.ON_NEW_METHOD` or `ON_ANY_CHANGE` requires a companion file to exist anytime the anchor file is modified, regardless of whether the specific method touched actually requires it.

**Policy**:
- This is a structural False Positive generated by the guard's lack of AST-level method awareness.
- These violations MUST be logged as `unknown` root causes during the SHADOW run.
- They are **NOT** targets for `known_debt` masking, because we explicitly want to measure the volume of these False Positives to determine if we need an AST-level refactoring before ENFORCING mode.

## 3. Framework Ruleset Verification Status Matrix

> [!WARNING]
> **CUSTOM Ruleset Risk**: Projects that fail framework detection default to the `CUSTOM` ruleset. Because this fallback has not been verified, it may generate massive noise if applied to structurally unrecognized projects (e.g., `survey_service`). These projects MUST be excluded from SHADOW pools until explicitly verified.

## 4. False Negative (FN) Safeguard - TP Retention
A 0% FP rate is meaningless if the guard simply allows everything to pass. We must ensure that the Completeness Guard is still capable of catching genuine missing files.

- [ ] **Known TP Retention**: Verify that known TP scenarios (such as the original 16 missing `method-level annotation` cases in `ism`, or the `apc` missing companion files) are still correctly resulting in `WOULD_BLOCK` in the shadow logs. If the guard stops blocking known missing files, the collection must be halted and the logic reviewed.

## 5. Human-in-the-Loop Labeling
A raw `unknownBlockEvent` is just a signal. It must be manually investigated to determine if it is a True Positive (the guard correctly caught a missing file) or a False Positive (the guard blocked a valid SR).

- [ ] **Labeling Completion**: Every collected `unknownBlockEvent` must be investigated and labeled as `TP` or `FP` by a human developer.
  - *Tip: Use the `ShadowReportGenerator` to export the list of unknown violations.*
- [ ] **Root Cause Analysis for FPs**: If an event is labeled `FP`, its root cause must be documented.
  - **Extractor Debt**: The node or edge was completely missing in `project-graph.json`.
  - **Logic Bug**: The rule evaluated incorrectly.
  - **File-Level Over-Enforcement (Important)**: The graph connects files (DAO to XML), not methods. If a developer/planner touches the DAO but reuses an existing query in the XML, the XML requires no modification. However, the Guard's `ON_NEW_METHOD` rule will still demand the XML because it enforces at the *file level*. These cases should be explicitly labeled as `FP (File-Level Enforcement)` so we can measure how often this specific Blunt Enforcement disrupts actual workflows. 
    - **CRITICAL POLICY**: *File-Level Over-Enforcement FPs must be intentionally kept as `unknown` and are NOT targets for `known_debt` masking.* Do not add known_debt exceptions (e.g., ignoring a package) just to silence these FPs, as doing so will destroy our ability to measure this specific FP rate.

## 3. Enforcing Thresholds
Once the denominator is established and labeled, calculate the FP Rate:
`FP Rate = (Total FP Events) / (Total unknownBlockEvents)`

- [ ] **Target FP Rate**: The FP rate must be **<= 5%**.
  - > [!WARNING] 
  - > If the FP rate exceeds 5%, `ENFORCING` mode MUST NOT be activated. Instead, analyze the FPs, add them to `known_debt.json` if they are acceptable extractor debt, or fix the Guard's logic, and restart the SHADOW collection.

## Execution Workflow
1. Deploy the plugin with `CompletenessGuard` set to `SHADOW` mode.
2. Let developers work naturally.
3. Run `ShadowReportGenerator` weekly to monitor `unknownBlockEvents` volume.
4. Once volume thresholds are met, execute the manual labeling phase.
5. If FP Rate <= 5%, switch the `guardMode` configuration to `ENFORCING`.
